# OpenAI Codex 提示词工程调研

## 摘要

Codex 的核心优势不是某一段“神奇的系统提示词”，而是一套完整的 Agent Runtime 提示词架构：模型专属基础指令、强类型上下文片段、分层项目规则、运行状态差分、token 生命周期管理、结构化工具，以及由沙箱和审批系统提供的硬约束共同决定 Agent 的行为。

换句话说，Codex 没有把 prompt 仅仅当作文案，而是把它当作一个需要版本管理、按模型适配、动态编译并与执行系统协同工作的控制协议。

本报告基于 OpenAI Codex 开源仓库的客户端源码和模型目录进行分析。逐文件审阅固定在提交 [`7abf2a3`](https://github.com/openai/codex/commit/7abf2a3b5cbe08ca875d677dcd027528f9556152)。复核时仓库 `main` 为 [`c11fdc9`](https://github.com/openai/codex/commit/c11fdc944f116b5f995059db58ef01f179733122)，两者之间仅增加一个 Windows sandbox 相关提交，提示词链路相关文件没有变化。

## 调研范围与限制

本报告重点分析以下公开机制：

- 模型专属 `instructions_template`；
- developer/user 指令的结构化表达；
- `AGENTS.md` 项目指令发现与组合；
- World State 状态快照和差分渲染；
- token budget 与自动上下文压缩；
- 基础指令、会话内容和工具定义的请求装配；
- sandbox、approval 和 permissions 与提示词的分工。

公开仓库可以证明 Codex 客户端如何构造请求，但不能证明这些内容是线上产品的全部输入。服务端可能存在额外指令、实验参数或策略；内部评测集、模型后训练方法以及线上 A/B prompt 变体也没有完整公开。

## 核心结论

Codex 的请求可以抽象为：

```text
模型专属 instructions_template
        +
developer/user 指令
        +
AGENTS.md 项目规范
        +
当前环境与 World State 增量
        +
对话历史
        +
结构化工具定义
        +
沙箱、审批和权限状态
        ↓
Responses API 请求
```

这套架构的价值在于，它同时回答了五个问题：

1. Agent 应该遵循什么通用工程行为？
2. 当前仓库和目录有哪些局部规则？
3. 当前模型、工作目录和执行模式是什么？
4. Agent 能调用哪些工具，权限边界在哪里？
5. 长任务中哪些上下文应该保留、压缩或重新注入？

## 一、模型专属指令，而不是万能 Prompt

Codex 的模型目录为不同模型提供独立的 `instructions_template`。在审阅版本中，共有 9 个模型条目，指令模板长度约为 15,296 到 21,459 个字符。

模型消息配置不仅包含基础指令，还可以包含：

- `instructions_template`；
- `instructions_variables`；
- `approvals`；
- `collaboration_modes`；
- `auto_review`；
- `multi_agent`；
- `permissions`；
- `token_budget`；
- `guardian_v2`。

这意味着 Codex 没有假设一份 prompt 可以稳定适配所有模型。不同模型可能需要不同程度的自主性约束、工具调用指导、沟通规范、审批说明和上下文管理策略。

这也是第一个重要工程结论：**prompt 应当和模型版本绑定，并像其他模型配置一样接受版本管理和回归评测。**

源码：[models.json](https://github.com/openai/codex/blob/7abf2a3b5cbe08ca875d677dcd027528f9556152/codex-rs/models-manager/models.json)

## 二、用决策规则代替空泛人设

普通系统提示词经常使用“专业、严谨、深入思考、乐于助人”等形容词。这些描述方向正确，但很难直接转化成稳定、可观测的行为。

Codex 的指令更接近工程决策表：

```text
触发条件 + 默认动作 + 例外情况 + 完成标准
```

典型规则包括：

- 除非用户明确只要求方案、解释或讨论，否则默认完成实际修改；
- 修改前先阅读相关代码，遵循仓库已有模式；
- 工作区可能存在用户修改，不得随意回滚或覆盖；
- 测试范围应当与修改风险和影响面相匹配；
- 遇到障碍先自主排查，真正无法继续时再交还用户；
- 搜索优先使用 `rg`；
- 相互独立的读取操作应并行执行；
- 完成后必须说明实际验证结果；
- 没有运行过的测试不能声称已经通过。

这类规则把高级工程师的隐性经验变成了可以观察、评测和逐步改进的 Agent 行为。

## 三、约束完整工作流，而不只是最终回答

Codex 的指令覆盖完整工程循环：

```text
理解需求
→ 检查仓库和项目规则
→ 搜索、阅读相关代码
→ 确定修改范围
→ 编辑文件
→ 运行聚焦验证
→ 处理失败和边界情况
→ 汇报结果与限制
```

这与只优化“如何生成代码”的提示词有明显区别。软件工程 Agent 的主要风险往往发生在代码生成之外，例如：

- 没有读取现有实现就开始改；
- 把用户未提交的修改覆盖掉；
- 修改了错误的模块；
- 没有验证就宣布完成；
- 运行了与任务无关的昂贵测试；
- 在用户只提问时擅自修改代码；
- 在用户要求实现时只给出建议。

Codex 的 prompt 将这些过程行为也纳入了控制范围。

## 四、明确 Agent 的自主性边界

一个 Coding Agent 需要知道的不只是“能做什么”，还包括“什么时候应该做”。Codex 的规则会区分：

- 用户在提问或调研，此时不应擅自修改代码；
- 用户明确要求实现，此时应主动完成到验证阶段；
- 存在会显著改变范围、正确性或数据安全的歧义，此时应询问用户；
- 普通实现细节，可以根据仓库惯例自行决定；
- 工具失败时，应先尝试合理的替代路径；
- 涉及危险操作或额外权限时，应服从审批和沙箱机制。

这解决了 Agent 常见的两种失衡：该执行时停留在方案层面，以及不该执行时过度自主。

## 五、Prompt 是结构化上下文，不是一整块字符串

Codex 为不同来源的上下文定义了明确的角色和内容类型。例如 `DeveloperInstructions`：

- 实现统一的 `ContextualUserFragment`；
- 使用 `developer` role；
- 使用 `generic.developer_instructions` 内容类型；
- 由上下文系统负责装配，而不是伪装成普通用户消息。

源码：[developer_instructions.rs](https://github.com/openai/codex/blob/7abf2a3b5cbe08ca875d677dcd027528f9556152/codex-rs/core/src/context/developer_instructions.rs)

可以把这种设计理解为：

```text
Prompt 不是一段字符串；
Prompt 是多个带角色、类型、来源和生命周期的上下文片段编译后的结果。
```

它带来几个直接收益：

- 可以按优先级组织指令；
- 可以只更新变化的片段；
- 可以区分稳定前缀与动态尾部；
- 可以对不同上下文来源独立测试；
- 可以避免把运行时状态和用户自然语言混在一起。

## 六、AGENTS.md 将通用 Agent 变成项目内 Agent

Codex 会发现并组合项目中的 `AGENTS.md`。这让通用基础指令和项目局部规范形成分层关系：

- 基础 instructions 负责通用工程行为；
- 用户级指令负责长期个人偏好；
- 仓库根目录 `AGENTS.md` 负责项目级规范；
- 子目录 `AGENTS.md` 负责局部模块规范；
- 当前用户指令负责本次任务目标。

项目规则可以和源码一起版本化，还可以根据当前工作目录逐层细化。源码也为项目文档设置了字节预算，避免项目说明无限占用模型上下文。

源码：[project_doc.rs](https://github.com/openai/codex/blob/7abf2a3b5cbe08ca875d677dcd027528f9556152/codex-rs/core/src/project_doc.rs)

这种设计比把整个 README 或所有项目文档无差别塞入 prompt 更稳定，因为它同时处理了作用域、顺序和预算。

## 七、World State 让 Prompt 具备状态

Codex 会维护运行环境快照，并根据上一状态和当前状态计算需要注入的差异。

模型状态是一个明确例子：

- 保存当前模型；
- 保存上一模型；
- 判断模型是否发生变化；
- 只有变化时才生成 `ModelSwitchInstructions`；
- 没有变化时不重复注入。

源码：[world_state/model.rs](https://github.com/openai/codex/blob/7abf2a3b5cbe08ca875d677dcd027528f9556152/codex-rs/core/src/context/world_state/model.rs)

其基本思想是：

```text
上一轮状态 + 当前状态 → 需要发送的上下文增量
```

这样做可以减少重复 token、降低重复指令对注意力的干扰，并支持模型或运行模式在长任务中发生变化。

## 八、Token Budget 也是提示词工程

模型配置中的 `token_budget` 不只是一个上下文长度数字，还包含：

- 自动压缩触发阈值；
- 压缩前预留 buffer；
- fallback 压缩提示词；
- 接近阈值时的 guidance message；
- reminder message template。

这表明 Codex 将提示词工程扩展到了完整的上下文生命周期：

1. 什么时候接近上下文上限；
2. 什么时候应该压缩；
3. 压缩时保留什么；
4. 压缩之后怎样提醒模型继续遵守原任务；
5. 自动压缩失败时怎样回退。

很多 Agent 在前几轮表现正常，长任务中却逐渐遗忘要求。问题通常不只是基础 prompt 不够好，而是没有设计状态保存、压缩时机和压缩后的行为恢复。

## 九、工具能力通过结构化协议提供

Codex 不会只在自然语言中告诉模型“你可以使用终端”。工具以结构化 schema 进入请求，程序负责提供工具名称、参数结构、权限范围和执行结果；基础指令则规定 Agent 应该如何选择和使用这些工具。

两者的分工是：

```text
Prompt：决定何时调用、怎样组合、失败后如何恢复
程序：校验参数、执行操作、返回状态、实施权限边界
```

这比让模型通过文本约定模拟工具协议更加可靠，也更容易审计和测试。

## 十、安全不能只依赖 Prompt

Codex 的 prompt 会要求模型：

- 不执行破坏性 Git 操作；
- 不覆盖用户已有修改；
- 不绕过审批；
- 不接触或泄露凭据；
- 尊重沙箱和权限边界。

但是，真正的安全边界还来自程序实现中的：

- sandbox；
- approval policy；
- permissions；
- guardian；
- 命令分类；
- 工具调用限制。

因此，prompt 更接近控制面的软策略，沙箱和审批系统才是执行面的硬边界。只复制“不要执行危险命令”这样的文本，不会产生同等级别的安全性。

## 十一、系统提示词本身最强的地方

### 1. 规则具有较高可判定性

Codex 大量使用“如果 A，则执行 B；除非 C”的形式，而不是依赖模糊品质描述。这使规则更容易通过真实任务和回归测试验证。

### 2. 默认行为明确

它会明确 Agent 在没有额外说明时应该实施、调查、验证还是询问，减少模型在每个步骤上重新猜测用户意图。

### 3. 负面约束带有原因和例外

高质量负面规则不是简单写“永远不要”，而是说明禁止的风险以及允许例外的条件。这样既能降低危险行为，也不会让 Agent 在正常任务中完全失去行动能力。

### 4. 对现实工程环境有充分建模

脏工作区、并发修改、命令超时、工具不可用、长任务压缩、模型切换和测试成本都被视为正常运行状态，而不是偶发异常。

### 5. 沟通规范服务于工程协作

Codex 不只约束语气，还要求报告实际改动、验证结果、未运行的检查和剩余限制。这种输出更接近可审计的工程交付，而不是泛泛的聊天回复。

## 十二、最值得复用的设计原则

1. 为不同模型维护不同基础指令，不要迷信万能 prompt。
2. 多写可判断的条件规则，少写“专业、深入、仔细”等抽象形容词。
3. 同时规定任务执行过程和最终输出要求。
4. 将稳定规则、项目规则、用户任务和动态环境分层管理。
5. 为上下文片段建立 role、类型、来源和生命周期。
6. 只同步发生变化的运行状态，避免每轮重复全部环境信息。
7. 把长对话压缩作为核心架构，而不是上下文溢出后的补丁。
8. 用程序实现权限、工具和安全边界，不依赖模型自律。
9. 针对脏工作区、失败恢复和并发修改制定明确规则。
10. 使用真实任务和回归评测验证行为，不以 prompt 长度衡量效果。

## 十三、常见误区

### 误区一：Codex 强是因为系统提示词足够长

长度只是结果，不是原因。长 prompt 如果缺乏层次、条件和执行系统配合，只会增加注意力负担。

### 误区二：复制公开 Prompt 就能复制 Codex

公开 prompt 只能复制部分行为风格。实际能力还依赖模型本身、上下文装配、工具协议、状态管理、沙箱、审批和评测体系。

### 误区三：所有信息都应该永久保留在上下文里

Codex 对 token budget、压缩和状态差分的设计说明，可靠 Agent 需要管理信息生命周期，而不是无限累积原始对话。

### 误区四：安全规则写进 system prompt 就够了

模型指令不是可靠的安全边界。高风险能力必须由工具实现、权限系统和沙箱共同限制。

## 十四、最终判断

Codex 最值得学习的不是某两万字符的具体措辞，而是以下四个工程判断：

1. **Prompt 应当像代码一样维护。** 它需要按模型适配、版本固定、结构化组合和回归验证。
2. **Agent 行为应当写成决策协议。** 明确触发条件、默认动作、例外和完成标准。
3. **上下文应当作为状态系统管理。** 分层注入、差分同步、预算控制和自动压缩缺一不可。
4. **软规则必须配合硬约束。** Prompt 负责决策指导，工具、沙箱和审批负责执行边界。

只复制 Codex 的系统提示词，通常只能得到表面上的表达风格。要接近它的实际可靠性，需要连同模型适配、上下文编排、工具协议、状态管理、权限系统和评测方法一起设计。
