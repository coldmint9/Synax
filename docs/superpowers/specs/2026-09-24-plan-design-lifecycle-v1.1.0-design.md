# Plan 模式设计生命周期与项目会话工作空间

- **目标版本**：v1.1.0
- **日期**：2026-09-24
- **状态**：设计稿
- **范围**：Plan 模式、Agent Runtime、项目会话工作空间、设计稿预览与实施

## 1. 背景与目标

当前 Plan 模式主要通过 `human.ask` 和 `plan.propose` 承担两类不同工作：

1. 面向小问题的即时澄清；
2. 面向大任务的方案撰写、评审和实施确认。

两者混在同一种交互里，会让长设计文档被表单化，也让用户为了配合工作流而学习 Synax 的内部步骤。

本版本将大篇幅设计文档从 Ask 交互中分离出来，提供一套轻量的设计工具集和项目会话级工作空间：

- Markdown 是设计稿正文的唯一事实来源；
- 设计稿自动落盘，可在会话重启后恢复；
- 设计稿始终通过现有 Markdown 渲染链路预览；
- 设计稿可以在 Plan 或 Chat 中继续读取、修改和实施；
- 生命周期状态只记录进度和提供提示，不强制用户遵守状态机；
- 用户随时可以退出 Plan，继续按 Chat 逻辑对话。

## 2. 非目标

本版本不做以下事情：

- 不新增设计稿数据库正文表；
- 不新增 Markdown 渲染器；
- 不建立严格的设计文档 AST、DSL 或 checklist 解析器；
- 不把 Markdown checklist 自动转换成复杂 DAG；
- 不用生命周期状态阻止用户切换模式或继续对话；
- 不新增独立的设计稿编辑器页面；
- 不删除或破坏现有 `human.ask`、`plan.propose`、`plan.execute`。

## 3. 核心决策

### 3.1 Markdown 文件是事实来源

每个 Agent Session 使用当前已绑定的项目工作目录，在以下位置保存设计稿：

```text
<project-workdir>/.synax/designs/<session-id>/design.md
```

路径由服务端根据 `sessionId` 和当前项目工作目录生成。工具输入不得指定任意路径，避免绝对路径和路径穿越。

数据库或 `sessionMetadata` 只保存轻量索引：

```ts
interface SessionDesignMetadata {
  relativePath: string;
  revision: number;
  status: "draft" | "review" | "approved" | "implementing" | "completed";
  updatedAt: string;
}
```

旧会话没有该字段时视为没有设计稿，不需要迁移数据库。

### 3.2 状态机是提示，不是门禁

最小状态集合为：

```text
draft → review → approved → implementing → completed
  ↑        │         │              │
  └────────┴─────────┴──────────────┘
```

状态允许跳过、回退和重复进入。状态的作用是：

- 在界面显示当前设计阶段；
- 帮助会话恢复上下文；
- 为工具调用和时间线提供可读摘要。

状态不用于：

- 阻止用户退出 Plan；
- 阻止 Chat 继续工作；
- 自动启动实施；
- 要求用户先完成某个阶段。

`approved` 只表示设计稿当前可供实施，不等于用户已经要求执行。`design.implement` 仍必须由当前用户意图触发，并复用现有执行权限和审批机制。

### 3.3 设计稿展示“思路”，不暴露原始推理

设计稿需要让用户看懂方案是怎样形成的，但不把模型内部隐式推理当作产品内容。推荐章节如下，章节不强制解析：

```md
# 设计标题

## 背景与目标

## 当前证据

## 方案选择与取舍

## 设计方案

## 实施步骤

- [ ] Step 1 ...

## 验证方式

## 风险与未决事项
```

“当前证据”和“方案选择与取舍”让设计依据可审阅；“实施步骤”和“验证方式”让设计稿可以自然转入执行。工具只保存 Markdown，不维护第二套结构化计划模型。

## 4. 工具集

新增以下五个 Agent Runtime 工具：

### `design.read`

读取当前会话设计稿和元数据。

- 文件不存在：返回空设计稿和初始元数据，不阻塞会话；
- 返回 `content`、`relativePath`、`revision`、`status`、`updatedAt`；
- 只读取当前会话固定文件。

### `design.write`

完整写入当前设计稿。

```ts
{
  content: string;
  expectedRevision?: number;
  status?: DesignStatus;
}
```

规则：

- `content` 必须是 Markdown 字符串；
- `expectedRevision` 存在且不匹配时拒绝覆盖，并返回当前版本信息；
- 成功写入后 `revision` 加一；
- 默认将状态设置为 `draft`，显式传入状态时保留该状态；
- 使用临时文件写入后 `rename`，避免中断留下半个文件；
- 设计目录不存在时自动创建。

### `design.preview`

返回适用于前端渲染的设计稿快照。

- 返回当前 Markdown 原文和元数据；
- 不重复实现 Markdown 解析；
- 前端交给现有 `MarkdownRenderer`；
- 与 `design.read` 共用文件读取逻辑，避免两份读取规则。

### `design.transition`

更新提示性生命周期状态。

```ts
{
  status: DesignStatus;
  reason?: string;
}
```

状态只校验为已知枚举，不强制校验迁移来源。状态变更更新 `sessionMetadata.design` 和时间线摘要，不修改正文。

### `design.implement`

以当前设计稿作为实施上下文，启动现有普通执行流程。

```ts
{
  revision?: number;
  reason?: string;
}
```

规则：

- 需要当前用户明确表达实施意图；
- Plan、Chat、Goal 都可以调用；
- 若设计稿不存在，返回可恢复错误，不生成隐式空方案；
- 可选 `revision` 用于防止基于旧设计稿实施；
- 将完整 Markdown 和设计稿元数据加入执行上下文；
- 复用现有工作区绑定、权限、审批、工具挂载和执行记录；
- 启动前将状态提示性更新为 `implementing`；
- 成功或失败不删除设计稿；完成时由执行结果更新为 `completed` 或保留当前状态。

## 5. 工具挂载与模式行为

### Plan

Plan 模式挂载完整 `design.*` 工具，并保留现有规划读取工具。Plan Agent 可以先调查，再持续更新 Markdown，最后请求用户预览或实施。

### Chat

Chat 模式允许在当前会话有设计稿时读取、预览、修改和实施。用户不需要重新进入 Plan。普通 Chat 仍然可以只聊天，不会被设计稿流程打断。

### Goal

Goal 可以把设计稿作为目标上下文使用，但不额外增加设计状态门禁。Goal 的完成与设计稿状态相互独立。

### 模式切换和中断

- 切换模式不删除设计稿；
- 切换到 Chat 后，当前会话按照 Chat 逻辑继续；
- 设计动作中断只停止当前动作，已成功落盘的内容保留；
- 关闭窗口、重启或恢复会话时，从 Markdown 文件和索引元数据恢复；
- 实施失败不自动回滚设计稿正文和历史修订。

## 6. 后端实现边界

### 6.1 文件服务

在 Agent Runtime 内增加设计稿文件服务，集中负责：

- 计算当前会话固定的相对路径；
- 解析项目工作目录；
- 创建设计目录；
- 原子读写 Markdown；
- 校验 revision；
- 处理不存在、冲突、损坏和权限错误。

工具本身只编排参数、权限和时间线结果，避免五个工具各自实现文件规则。

### 6.2 元数据

扩展现有会话元数据类型，增加可选 `design` 字段。元数据必须兼容旧会话和旧客户端；读取未知字段时不影响现有会话。

正文不复制到数据库，避免文件和数据库双写导致事实来源分裂。

### 6.3 执行复用

`design.implement` 不复制 `plan.execute` 的执行器。它只负责：

1. 读取并校验设计稿；
2. 把设计稿转成当前执行轮次的上下文；
3. 调用现有执行流程；
4. 更新提示性状态和事件。

原有 `plan.propose` / `plan.execute` 继续支持结构化的一次性执行计划，作为兼容路径保留。

## 7. 前端实现边界

复用 `web/src/react/components/markdown/MarkdownRenderer.tsx`，不新增渲染器。

会话工作区增加轻量设计稿入口，至少展示：

- 是否存在设计稿；
- 当前状态；
- 当前 revision；
- 最后更新时间；
- Markdown 渲染后的正文；
- 设计工具调用和修订摘要。

设计稿入口可以嵌入现有会话工作区或时间线，不要求独立页面。编辑能力优先复用现有会话输入和 Agent 工具，避免再维护一个大型富文本编辑器。

Ask 面板继续服务短问题澄清和必要确认；长文档由设计稿预览承载。

## 8. 错误处理与安全

- 设计目录不存在：返回空稿；
- 文件不存在：等价于空稿；
- `expectedRevision` 冲突：返回冲突和当前版本，不静默覆盖；
- 路径穿越或绝对路径：拒绝；
- 设计稿无法读取：报告可恢复错误，不阻塞 Chat；
- 原子写失败：保留原设计稿，返回失败；
- `design.implement` 继续使用现有权限和工具审批，不绕过安全边界；
- 不把凭据、内部权限信息或原始隐式推理写入设计稿作为工具要求。

## 9. 测试与验收

最小测试覆盖：

1. 新会话读取不存在的设计稿时返回空稿；
2. 写入创建目录和 Markdown 文件；
3. revision 成功递增；
4. revision 冲突不会覆盖旧文件；
5. 路径固定且拒绝路径穿越；
6. 状态可以自由跳过和回退；
7. Plan 和 Chat 都能挂载/调用设计工具；
8. Chat 能对已保存设计稿启动实施；
9. 切换模式不会删除设计稿；
10. Markdown 预览经过现有渲染器显示标题、列表、代码块和表格；
11. 旧会话无 `design` 元数据时保持兼容。

版本更新使用项目现有版本脚本：

```sh
npm run version:minor
```

目标结果为 `SYNAX_VERSION=1.1.0`，并同步 package、lockfile 和代码中的版本号。

## 10. 实施顺序

1. 增加设计稿元数据类型和文件服务；
2. 增加五个 `design.*` 工具及工具挂载规则；
3. 接入会话时间线和运行时事件；
4. 增加前端会话设计稿入口与 Markdown 预览；
5. 增加后端和前端最小测试；
6. 执行版本 minor 同步到 v1.1.0；
7. 运行 typecheck、lint 和相关测试。

## 11. 验收结论

完成后，用户可以在 Plan 中形成设计稿，也可以随时退出 Plan 继续 Chat；设计稿会自动落盘并可预览，用户明确要求时可在任意允许的会话模式中实施。状态机只帮助系统恢复和展示进度，不把用户变成工作流的操作员。
