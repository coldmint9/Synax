# Synax Electron-hosted Cua Computer Use with Optional Jev

- **Date:** 2026-09-28
- **Status:** Design approved for review; implementation not started
- **Scope:** Synax desktop application, Native Agent backend, Electron-hosted Cua Driver Runtime
- **Base:** `main` at `0de82e5`

## 1. Context

Synax is adding desktop Computer Use through Cua Driver. The selected runtime architecture is:

```text
Electron Main Process
  └── EmbeddedCuaDriverHost
        └── Cua Driver Runtime

Synax API Sidecar
  └── Synax MCP client
        └── Cua Driver MCP proxy

Synax Native Agent
  └── Synax ToolRegistry
```

Cua Driver's current upstream work distinguishes two related capabilities:

- PR #3943, merged on 2026-09-22, adds the optional `cua-perception` visual-region extension and the `parse_visual_regions` contract.
- The `jev-use` recipe is a separate integration boundary. Jev chooses from application-created, complete candidate actions; it does not generate arbitrary Cua tool names or arguments.

## 2. Decision summary

### 2.1 Direct Cua is the default

When no Jev API configuration is present, Synax uses the normal Cua Computer Use path:

```text
Synax Agent
  → Cua MCP tools
  → Cua Driver
  → desktop / browser / native app
```

No Jev client is initialized, no Jev request is made, and no Jev dependency is required for runtime behavior.

### 2.2 Jev is an explicit optional strategy

Jev is enabled only when the user explicitly configures it. When enabled, Synax uses a `ComputerUseController` that:

1. observes through Cua;
2. builds a bounded set of complete candidate actions;
3. asks Jev to choose a candidate ID;
4. validates the returned ID and confidence data;
5. runs Synax permission checks;
6. executes exactly one Cua action;
7. re-observes and verifies the result.

Jev never generates raw Cua arguments, coordinates, tokens, window IDs, or tool names.

### 2.3 `cua-perception` is independently optional

Jev and `cua-perception` are separate switches. Semantic Accessibility Tree / DOM evidence is preferred. Visual-region parsing is used only when explicitly enabled and available. The default Synax desktop package does not bundle the optional visual extension until licensing and distribution are approved.

## 3. Goals

1. Add Cua Driver to the Synax desktop application without moving native desktop permissions into the API sidecar.
2. Preserve the existing Synax MCP, Agent ToolRegistry, permission, media-asset, and session lifecycle abstractions.
3. Keep normal Direct Cua behavior fully functional without Jev configuration.
4. Add Jev as a bounded, auditable action-selection enhancement.
5. Keep Cua sessions isolated per Synax Agent Session.
6. Prevent replay of Cua side effects after an unknown transport outcome.
7. Preserve Cua MCP input schemas, structured content, screenshots, element tokens, snapshot IDs, capture IDs, and verification data.
8. Make mock Jev execution deterministic and credential-free for tests.

## 4. Non-goals

1. Do not replace Synax's Native Agent loop.
2. Do not require Jev for Cua Driver installation or Direct Cua mode.
3. Do not make Jev a dependency of Electron Main Process.
4. Do not make the first release support arbitrary, unbounded desktop workflows generated by visual coordinates.
5. Do not bundle `cua-perception` by default before license review and artifact-distribution decisions.
6. Do not change ACP providers in the first implementation. Synax's non-native backends already manage MCP through their own native configuration path.
7. Do not automatically fall back from an explicitly configured but unavailable Jev service unless the user selects `fallback: direct`.

```text
┌───────────────────────────────▼──────────────────────────────┐
│ Synax API Sidecar                                             │
│                                                              │
│  McpClientManager                                             │
│    └── session-scoped `cua-driver mcp` proxy                 │
│                                                              │
│  ComputerUseController                                       │
│    ├── DirectCuaAdapter                                      │
│    ├── JevDecisionService (lazy, optional)                   │

│    └── `computer.use` in Jev mode                            │
└──────────────────────────────────────────────────────────────┘
```

### 5.1 Electron Main responsibilities

Electron Main owns:

- `EmbeddedCuaDriverHost` creation;
- Cua Runtime start, restart, and stop;
- native permission responsibility on macOS;
- Cua MCP connection generation;
- passing the current connection to the API sidecar;
- orderly shutdown after Agent work and MCP clients stop.

Electron Main must not own Jev API clients, candidate construction, or Agent decisions.

### 5.2 API Sidecar responsibilities

The API sidecar owns:

- the Synax MCP client connection to the Cua proxy;
- Cua MCP tool discovery and invocation;
- direct-mode tool exposure;
- the optional `ComputerUseController`;
- the optional Jev adapter and provider credentials;
- candidate validation and result verification;
- session-level Cua connection isolation.

## 6. Strategy model

```ts
type ComputerUseStrategy = "auto" | "direct" | "jev";

type JevFallback = "direct" | "fail_closed";

type PerceptionMode = "disabled" | "auto" | "required";

interface ComputerUseConfig {
  enabled: boolean;
  strategy: ComputerUseStrategy;
  jev?: {
    enabled: boolean;
    providerId: string;
    model?: string;
    fallback: JevFallback;
  };
  perception: PerceptionMode;
}
```

Defaults:

```json
{
  "enabled": true,
  "strategy": "auto",
  "jev": {
    "enabled": false,
    "fallback": "fail_closed"
  },
  "perception": "disabled"
}
```

### 6.1 Strategy resolution

| Configuration | Effective behavior |
|---|---|
| `enabled=false` | Computer Use unavailable |
| `strategy=direct` | Direct Cua regardless of Jev configuration |
| `strategy=jev` and valid Jev config | Jev-assisted Cua |
| `strategy=jev` without valid Jev config | Configuration error; no action |
| `strategy=auto` without Jev config | Direct Cua |
| `strategy=auto` with valid Jev config | Jev-assisted Cua |
| Jev configured but unavailable | `fail_closed` by default; explicit `direct` fallback is allowed |

Missing Jev configuration must not make Cua startup fail.

### 6.2 Direct mode

Direct mode exposes the Cua MCP tools through the existing `mcpSessionToolProvider`. The following safety and fidelity improvements apply in all modes:

- preserve MCP `inputSchema` and convert it to the Synax Zod schema;
- preserve MCP `structuredContent` in the tool result;
- import MCP image content into Synax project assets;
- disable automatic retries for Cua side-effect tools;
- isolate Cua MCP connections per Agent Session;
- retain Synax permission gating and Cua Runtime permission enforcement.

### 6.3 Jev mode

Jev mode exposes a model-facing `computer.use` tool and keeps raw Cua tools internal to the controller. The first implementation performs at most one Cua side-effect action per `computer.use` call.

A Jev request contains:

- a short user/Agent goal;
- compact observation data;
- immutable candidate IDs and descriptions;
- optional redacted history;
- optional validated visual-region metadata;
- no screenshot bytes unless a future provider contract explicitly requires them.

A Jev response must be validated for:

- known candidate ID;
- finite confidence between 0 and 1;
- finite probabilities between 0 and 1;
- no unknown probability keys;
- no stale observation/capture binding;
- valid reserved choices such as `reobserve` and `abstain`.

## 7. Electron Cua Runtime lifecycle

### 7.1 Startup

```text
Electron app ready
  → resolve Cua Driver executable
  → start EmbeddedCuaDriverHost
  → obtain generation-scoped MCP connection
  → start API sidecar with Cua bootstrap data
  → allow Agent sessions
```

### 7.2 Runtime restart

```text
stop accepting new Cua work
  → interrupt or drain active Cua sessions
  → close old MCP clients
  → restart EmbeddedCuaDriverHost
  → send replacement MCP connection to API sidecar
  → resume new Cua work
```

The old generation, socket path, and MCP process must not be reused after restart.

### 7.3 Shutdown

```text
stop accepting new Agent work
  → close Cua MCP clients
  → stop API sidecar
  → shutdown Cua driver client
  → stop EmbeddedCuaDriverHost
```

No action is replayed automatically after a Cua process exits with an unknown result.

## 8. API sidecar bootstrap

`startSidecar` receives a generation-scoped Cua MCP connection from Electron Main. The sidecar creates a runtime-only, internal configuration entry:

```ts
interface RuntimeCuaMcpConfig {
  id: "builtin-cua-driver";
  command: string;
  args: string[];
  environment?: Record<string, string>;
  generation: string;
}
```

This configuration is not persisted as a user project MCP server. It is invalidated when the generation changes.

The sidecar should initially receive bootstrap data through a controlled local bootstrap channel. Environment-variable injection may be used in development, but production should avoid placing a large serialized connection object in a long-lived process environment.

## 9. MCP client changes

### 9.1 Tool definition fidelity

Extend `McpRuntimeToolDef` with:

```ts
inputSchema?: Record<string, unknown>;
outputSchema?: Record<string, unknown>;
```

`mcp-session-tool-provider.ts` converts `inputSchema` using `z.fromJSONSchema`. The generic catch-all object schema remains the fallback for malformed or absent schemas.

### 9.2 Structured results

Extend MCP call results with:

```ts
structuredContent?: unknown;
isError?: boolean;
```

The provider must return structured Cua data including:

- `snapshot_id`;
- `capture_id`;
- `element_token`;
- `window_id`;
- `elements`;
- action effect and refusal metadata;
- verification information.

### 9.3 Retry policy

Add a Cua-specific retry policy. Read-only observation calls may retry according to a bounded policy. Side-effect calls such as click, type, keypress, launch, kill, and clipboard write must not be replayed after an ambiguous transport failure.

### 9.4 Session isolation

Add a lifecycle setting for MCP servers. Cua uses session-scoped clients:

```ts
type McpLifecycle = "project" | "session";
```

The Cua client cache key is effectively:

```text
projectId + serverId + sessionId
```

Existing MCP servers retain project-scoped behavior unless explicitly marked session-scoped.

## 10. Direct Cua tool behavior

Direct mode follows the normal Cua pattern:

```text
observe
  → select semantic element or exact window
  → perform one action
  → observe again
  → verify postcondition
```

The built-in Computer Use skill instructs the Agent to:

1. observe before acting;
2. prefer Accessibility Tree / DOM evidence over pixels;
3. use fresh element tokens and snapshot IDs;
4. re-observe after window or page changes;
5. use background delivery by default;
6. never silently convert a refused background action into a foreground action;
7. verify important state changes;
8. avoid unnecessary screen and clipboard access.

## 11. Jev controller behavior

`ComputerUseController` is a Session-scoped service. It does not expose the TypeSafe Jev client to the Agent.

### 11.1 Candidate construction

Candidates are generated by Synax adapters from fresh observations. Each candidate contains the complete Cua action arguments and observation binding. Candidate IDs are unique, short, and opaque.

Every candidate set includes:

- at least one executable or recovery candidate;
- `reobserve`;
- `abstain`.

A candidate is invalid if its snapshot or capture binding is stale, missing, ambiguous, out of bounds, or inconsistent with the observation used to construct it.

### 11.2 One-action boundary

The controller performs a maximum of one side-effect action per Agent Tool call. The next action requires a new observation and a new decision. This keeps Synax permission prompts and runtime events aligned with actual side effects.

### 11.3 Verification

Action success is not inferred from the Cua action acknowledgement alone. The controller obtains fresh state and evaluates the requested postcondition. Verification may use:

- Cua structured action result;
- fresh Accessibility Tree;
- fresh browser semantic snapshot;
- independent application endpoint where available;
- optional visual-region evidence.

## 12. Optional visual perception

`perception=disabled` is the default. With `perception=auto`, the controller may use `parse_visual_regions` when:

1. the Cua Driver advertises the tool;
2. the exact capture-bound contract is available;
3. the current semantic observation is insufficient;
4. the visual result passes schema, geometry, confidence, uniqueness, and capture binding validation.

The controller never downgrades a validated visual result into an unbound screen-coordinate click. A capture mismatch or stale capture is a hard refusal.

The default Synax distribution does not bundle `cua-perception` until license, artifact, and update policy are approved.

## 13. Permissions and security

There are three distinct permission layers:

1. Synax Agent permission policy;
2. Cua Driver permission mode and capability manifest;
3. operating-system permissions such as macOS Accessibility and Screen Recording.

Jev cannot expand any of these permissions.

Direct Cua tools and `computer.use` both use Synax permission category `mcp` or a dedicated `computer_use` capability mapped to the existing external-execution approval surface. The first implementation retains the existing explicit MCP approval behavior.

Jev credentials are loaded only in the API sidecar through a protected provider connection or environment-backed secret. They are never placed in:

- MCP tool arguments;
- Agent-visible messages;
- candidate descriptions;
- logs;
- screenshots;
- artifacts.

## 14. Configuration ownership

Project settings own:

- whether Computer Use is enabled;
- Direct/Jev strategy;
- Jev provider reference and model;
- visual-perception mode;
- explicit Jev failure fallback.

Secret values are stored through the existing provider-connection / secret mechanism and are not persisted in plain project JSON.

The runtime-generated Cua MCP connection remains Electron-owned and is not editable in the normal MCP settings UI.

## 15. Observability

Record safe metadata only:

- strategy: direct or jev;
- session ID and Cua generation ID;
- Cua tool name;
- candidate ID, not sensitive candidate payload;
- Jev confidence and selected model, when available;
- observation/snapshot/capture identifiers;
- permission decision;
- verification outcome;
- refusal or stale-binding code;
- duration and retry decision.

Do not record:

- screenshots by default;
- raw typed text;
- clipboard contents;
- Jev API keys;
- full candidate action arguments when they contain secrets;
- raw accessibility trees unless the user explicitly enables diagnostic capture.

## 17. Testing strategy

### Unit tests

- strategy resolver with absent, disabled, direct, auto, and Jev configurations;
- lazy Jev initialization does not occur in Direct mode;
- Jev response candidate validation;
- unknown candidate, invalid confidence, invalid probability, abstain, and reobserve;
- Cua input schema preservation;
- Cua structured content preservation;
- Cua image asset import;
- Cua side-effect retry suppression;
- session-scoped MCP cache keys;
- runtime generation invalidation;
- redaction of secrets and typed values.

### Integration tests

- Electron bootstrap injects a Cua MCP connection into the API sidecar;
- Direct mode can call `list_apps`, `get_window_state`, and an observation tool without Jev;
- Jev mode calls the mock Jev adapter and executes the selected candidate;
- Jev mode does not expose raw Cua tools to the model;
- explicit Jev failure fallback follows configuration;
- Cua restart invalidates the old generation;
- unknown action outcomes are not replayed.

### Desktop smoke tests

1. start Calculator;
2. observe the Calculator window;
3. Direct mode enters `42` and verifies it;
4. Jev mock mode selects from the candidate table and verifies it;
5. disable Jev and repeat using Direct mode;
6. revoke Screen Recording or Accessibility permission and verify a clear refusal;
7. restart the Cua Runtime and verify old MCP connections are not reused.

- no Jev dependency;

### Stage 2: Jev mock mode

- protected provider connection;

- visual acceptance tests.

## 19. Acceptance criteria

The design is considered implemented when:

1. A Synax desktop build can start and stop an Electron-hosted Cua Runtime.
2. Direct Cua works without any Jev configuration or network access to Jev.
3. Direct mode preserves Cua schemas, structured results, images, and verification metadata.
4. A Cua side-effect action is never automatically replayed after an ambiguous transport failure.
5. Two concurrent Synax Agent Sessions do not share one Cua lifecycle connection.
6. Jev can be enabled without changing Electron Main's native permission ownership.
7. Jev receives only bounded observations and candidate descriptions and returns a validated candidate ID.
8. Jev can be disabled and Direct Cua resumes without reinstalling or restarting Synax.
9. Optional visual perception is capability-detected, capture-bound, and disabled by default.
10. No Jev API key or sensitive desktop content appears in logs or Agent-visible output.
