01 / 愿景与价值

让研发任务
从“被安排”走向“持续交付”

奥创知道团队要做什么、为什么做。
Synax 让 Agent 在合适的环境中把任务做出来，并交回可以检查的结果。

奥创 · 研发协作与规划中心
管目标、知识和进度

像项目负责人：明确需求，排好优先级，提供资料，组织验收。

Synax · 研发执行工作台
管执行、验证和接管

像工程师的工作间：打开代码，执行任务，检查结果，遇到问题请人决策。

用户体验：在奥创安排一个任务，在 Synax 开始工作；需要时交给远端继续，再回到同一条任务记录审查结果。

02 / 产品边界

一件事只由一个地方说了算

“事实源”可以理解为最终记账的地方。避免奥创显示任务已完成，Synax 却仍在修改代码，或者两边都能改需求却相互覆盖。

问题建议由谁负责另一方怎么配合
要做什么？先做哪个？奥创：需求、迭代、优先级、依赖Synax 读取可执行任务
依据哪些资料？奥创：知识、文档与版本Synax 记录本次使用的资料快照
代码改到哪里了？Synax Runtime：执行、工具与变更记录奥创展示进度和证据引用
现在在哪台机器执行？执行协调服务：节点与执行权两端查看同一份执行位置
业务上算完成了吗？奥创：按验收规则收口Synax 提交测试、差异和审查结果
最重要的一条：Agent 结束一轮对话，只说明这一轮停止了。测试通过、验收通过、任务关闭是不同的事件。

04 / 能力映射

奥创的每项能力，在 Synax 中产生什么价值？

奥创能力带到 Synax 的内容用户直接获得的价值
需求树当前需求、父级目标、验收条件Agent 理解业务目的，减少“改对代码、做错需求”
迭代池待执行任务、优先级、依赖与负责人直接领取任务，知道哪些已具备开工条件
知识相关规范、领域术语、历史决策减少重复解释，保持团队开发习惯
文档接口定义、设计稿、规格与版本引用代码修改有依据，事后可查当时参考了什么
工作流阶段、审批、依赖与交付规则清楚下一步交给谁，哪些步骤要等人批准
AWG 工作流可执行节点与输入输出约定，待接口确认有条件地把多个研发执行组合为完整流程
会话池任务关联的会话索引、状态与历史从任务找到讨论、执行和阻塞现场
资料带入方式：保留奥创中的原始引用，同时记录执行时的版本。资料很多时按任务检索，而不是把整个知识库塞进每次对话。

奥创 → Synax

交接包里需要带什么？

任务与上下文

目标、验收条件、文档版本、执行计划、已完成与待完成事项。

代码与环境

基准提交、未提交补丁、必要文件、工具链与依赖声明；临时目录不能默认可恢复。

运行与等待状态

事件位置、检查点、待答问题、未确认操作；终端与浏览器状态单独判断能否重建。

执行权与授权

旧节点停止确认、新节点取得执行权；远端重新取得所需凭据与权限。

掉线不等于停机。不能因为收不到心跳就立刻让两台机器同时写。需要租约与过期执行者拦截机制；无法确认安全状态时，先阻塞并让人处理。接入外部系统的写操作还需要幂等或对账。

08 / 编排边界

外层管协作，内层管具体工作

奥创工作流 / AWG · 跨任务编排

需求澄清→研发执行→审查验收→发布流程

决定阶段依赖、任务参与者、审批位置与失败分支。AWG 是否能直接调用 Synax，需要核对真实接口与执行语义。

“研发执行”节点调用一个或多个 Execution

Synax · 单项任务执行

读代码→分析与修改→测试与复查→提交证据

管理工具调用、代码变更、执行限制与人工交互。外层任务的“批准”不能自动变成全部工具的无限授权。

会话池如何与任务关联？

需求 / 迭代任务 T-104 └─ Execution E-028：这一次研发工作 ├─ Session A：分析与实现 │ ├─ Run 1：理解需求 │ └─ Run 2：修改与测试 └─ Session B：审查或接续（需要时创建）

Execution 是建议新增的跨系统标识。一个任务可以有多次执行，一次执行可以关联多个会话。跨节点时不强求各个 Agent 后端都能迁移原生会话，必要时依据交接包创建新会话。

09 / 一致性与可追溯

几条容易理解、但不能省略的约定

约定通俗解释解决的问题
唯一执行身份每次工作都有自己的单号本地、远端、奥创查的是同一项工作
幂等提交按钮点两次、网络重试，都只创建一次避免重复开工、重复回写
单一执行权同一执行工作区在同一时间只有一个主执行者避免两个节点互相覆盖；并行子任务使用隔离工作区
事件序号与对账知道上次读到第几条，断线后补齐，并核对最终状态不丢进度、不因重连重复启动
上下文版本知道当时看的需求和文档是哪一版需求中途变化时可以比较差异、决定是否重新规划
证据绑定代码版本测试结果必须对应实际交付的代码避免拿旧测试证明新代码正确
节点独立授权本地能做的事，远端要重新确认具备条件防止不合适的凭据、目录或工具权限被直接复制
回写奥创失败时，保留本次结果并重试同步，界面标记“待同步”；不要把业务回写失败误当成代码任务需要重新执行。
10 / 落地路径

先证明有用，再增加执行规模

每个阶段都用一个真实任务验收。以下为推进顺序建议，不是开发工期承诺。

第一阶段

任务接入闭环

  • 读取奥创任务与相关资料
  • 绑定项目、会话与执行记录
  • 本地执行和人工审查
  • 回写结果与证据引用

验收：一个真实任务可以从领取到验收完成；断线重试不重复创建执行。

第二阶段

远端执行与交接

  • 优先支持直接在远端开工
  • 再引入检查点迁移
  • 节点授权、隔离与执行权
  • 掉线、失败与恢复处理

验收：交接前后任务和证据连续，旧节点不能继续写入同一执行。

第三阶段

工作流协同

  • 对接工作流 / AWG 节点
  • 依赖、审批与失败分支
  • 多执行的统一观察
  • 经审核的知识回流

验收：多阶段任务可暂停、恢复与审查；失败能定位到对应执行。

优先选择：先做好“同一个远端执行可从不同客户端观察与接管”，再做“运行地点从本地迁到远端”。前者无需搬迁正在运行的进程，更容易验证价值。
当前依据应如何理解
Synax 已有 Session / Run / Step、工作区与运行协议基础来自前次仓库和文档检查，可以作为集成起点；具体接口仍需实施前核验。
仓库存在 local-node、cloud-node、worker 目录只能说明已有节点相关结构，不能据此宣称跨节点接续已经完成。
跨节点租约、完整交接包与奥创连接器本提案中的新增设计，需开发与验证。
11 / 决策与答疑

下一步先定边界，再定页面

建议先采用

  • 奥创保管研发目标与知识原件
  • Synax 保管执行事实与证据
  • Execution 贯穿整个任务过程
  • 在检查点进行跨节点交接

需要一起确认

  • 奥创可用 API 与身份授权方式
  • AWG 节点及回调的真实约定
  • 会话池是会话记录还是资源调度池
  • 远端部署地点及数据范围
为什么不直接把奥创页面嵌入 Synax？

嵌入页面可以作为快捷入口，但任务、代码、会话与验证结果仍可能是分离的。连接任务身份和执行记录后，面板才能准确告诉用户任务在哪里执行、为什么阻塞、交付了什么。

关掉 Synax 后，任务能继续吗？

远端运行且不依赖本地资源的任务，可以设计为继续执行。仅关闭观察界面与关闭执行节点是两回事。本地电脑休眠后，本地进程通常无法继续；要保持运作，需提前在远端启动或完成受控交接。

“共享会话”是否就等于“无缝迁移”？

不等于。聊天记录没有包含全部文件、进程、授权和外部操作状态。接续应以可恢复的检查点为基础，遇到不能恢复的步骤要显式重建、重试或人工处理。

任务能不能自动跑到完成？

可以在明确任务范围、验收规则和授权边界内持续推进。遇到需求歧义、权限不足、证据不通过或发布审批时，应进入等待状态，保留进度并通知相关人员。

远端返回的知识能否直接成为团队规范？

建议先生成知识变更建议，标明依据和关联任务，由负责人审阅后发布。Agent 的执行摘要与正式团队规范应有不同的状态。

路演主张：让奥创中的研发意图，进入 Synax 中可观察、可接管、可验证的执行过程，最终带着证据回到奥创。
