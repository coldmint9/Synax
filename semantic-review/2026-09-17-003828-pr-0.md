# AgentSession 去除 blocked/paused 后的运行态收敛

本次改动从 AgentSession 契约、持久化、控制面和前端状态中移除了 `blocked`/`paused`，同时保留 Run、Step 与 Goal 的 `blocked` 结果，用 `completed + blockedReason` 表达 Session 已停止但未成功。`round_yielded` 依靠最新 Run 的 stop reason 与 Goal/Plan/Work 一致性门控创建下一轮，普通 `completed` 的无输入 continue 在 admission 与 loop 两层拒绝。当前仍有四个跨层缺陷会造成强制指令无执行出口、悬空 Run，或错误的用户可见状态。

Watch for: **[confirmed, High]** round handoff 后的强制队列输入会同时阻止自动续跑且无法自行启动；**[confirmed, High]** 权限超时把 Session 置为 completed，却保留 waiting_permission Run/Step；**[confirmed, Medium]** Synax 的 failed/cancelled/interrupted 被投影成 completed；**[confirmed, Medium]** waiting_permission 被投影成 waiting_input 后，权限通知、刷新和排队逻辑仍依赖 waiting_permission。

**Verdict**: NEEDS_CHANGES

## High-level view

`round_yielded` 门控遇到 force-inject 输入时会放弃系统续跑，但后续队列调度又拒绝 `round_yielded` 和未完成 Work。强制输入既不进入下一轮，也不恢复原 Goal，Session 停在 completed。

权限超时把 Session 收敛为 completed，却没有把对应 Run/Step 结算为仍合法的 blocked。清空 `activeRunId` 后，新请求可绕过等待态保护，与旧 waiting_permission Run 并存。

Synax 专属投影超出了 blocked/paused 归一化范围，把失败、取消、中断对外改写为 completed。取消响应、恢复确认、列表 histogram 与前端 patch 因此丢失终态原因和恢复入口。

同一投影还把 waiting_permission 改写为 waiting_input，但权限消费者没有迁移到新信号。后台审批 toast 和 Goal 权限刷新不会触发，Composer 也失去审批期间的排队能力。

## 强制输入在 round handoff 后进入无出口状态

**[confirmed, High]** `goalContinuationInput` 在存在 force-inject ID 时返回 `null`（`api/services/agent-runtime/goal-continuation.ts:22-24`），RunCoordinator 随后转入 `dispatchQueuedInput`（`api/services/agent-runtime/run-coordinator.ts:193-195`）。该调度器却拒绝最新 Run 为 `round_yielded`、以及 Work 尚未 completed 的 Session（`run-coordinator.ts:86-89`）；这两项正是继续中的 Goal handoff 的状态。用户在 handoff 落盘后或收尾竞态窗口内点击“强制插入”，会得到成功的 force 响应，但没有新 Run，自动 continuation 也已被禁止。

```text
round_yielded + active Work
          |
          +-- force ID -> goalContinuationInput = null
          +-- dispatchQueuedInput -> rejects round_yielded/active Work
          `-- Session completed, queue retained, no owner
```

最小修复是在 coordinator 中给 forced item 单独的 handoff 接管路径：允许它在 `round_yielded + active Work` 上创建 continuation Run，以用户消息继续同一 Goal，并在 admission 成功后原子消费 force ID；普通队列仍等 Goal 完成。应增加 coordinator 到 force route 的组合测试，断言输入只执行一次且 Goal/Work identity 不变。当前测试只断言 `goalContinuationInput()` 返回 `null`，没有验证后续执行出口。

## 权限超时留下 completed Session 与 waiting Run/Step

**[confirmed, High]** `sweepExpiredPermissions` 解决 permission 后直接把 Session 更新为 completed、清空 `activeRunId` 与 resume token（`api/services/agent-runtime/permission-timeout-sweeper.ts:62-71`），却没有更新 permission 所属 Run、Step 或 pending tool call。由于 admission 只把 queued/running Run 视为 active，并只在 Session 为 waiting_permission 时拒绝新执行，超时后的 completed Session 可以接受新 Run，旧 waiting_permission Run 继续留在同一 lineage；重启 recovery 还会把旧 Run 识别为 safe checkpoint。

最小修复是把超时结算放进一个事务：根据 permission 的 `runId`/`stepId` 将 Run 和 Step 标为 blocked、写入完成时间与 stop reason，并将 pending tool call 标为 denied/cancelled，再将 Session 收敛为 completed。若需要模型生成拒绝后的说明，应复用正常 reject resume 路径。应使用真实 store 测试 Session/Run/Step/tool 的联合终态和后续 admission；现有 sweeper 测试只 mock Session 更新。

## Synax 终态被误报为 completed

**[confirmed, Medium]** `projectSessionState` 对 `synax`/`goal` 只保留 queued、running 与 waiting_input，其余状态一律返回 completed（`api/services/agent-runtime/session-projection.ts:39-47`）。`agentSessionRuntime.cancel()` 写入的 interrupted 在 cancel 响应被改写（`api/routes/agent-runtime.ts:296`），`acknowledgeRuntimeRecovery()` 的 interrupted 在恢复响应也被改写（`agent-runtime.ts:543-544`），failed 同样进入 completed histogram。前端又把 failed/cancelled/interrupted 改成 completed（`web/src/react/features/sessions/sessionComposerState.ts:18-20`），而恢复按钮只对 interrupted/failed 可见（`sessionComposerState.ts:66-68`；`AgentConversationView.tsx:46-48`）。停止、失败和恢复后的会话因此显示为普通完成，并失去无输入 resume 入口。

最小修复是把投影限制为 legacy `blocked`/`paused -> completed`，保留 failed/cancelled/interrupted，并让 SQL 与前端共享该映射。若三态 Synax UI 是产品约束，则需保留独立 terminal outcome，让取消响应、错误通知和 resume 控件使用它。应补充 cancel、failed、recovery acknowledge 的 API-to-UI 契约测试。

## waiting_permission 归并后权限消费者失去信号

**[confirmed, Medium]** Synax waiting_permission 在服务端投影为 waiting_input（`api/services/agent-runtime/session-projection.ts:39-42`），前端 patch 也执行同样改写（`web/src/react/features/sessions/sessionComposerState.ts:17`）。全局 notifier 只在 `patch.status === "waiting_permission"` 时发 toast（`web/src/hooks/useAgentPermissionNotifier.ts:37-38`），Goal bridge 也只在 waiting_permission/running 时刷新 permissions（`web/src/react/features/wiki/goal/useGoalSessionBridge.ts:74-76`）。HTTP event stream 先应用服务端投影，因此这些消费者实际收到 waiting_input；现有 notifier 测试手工注入 waiting_permission，未覆盖真实 wire 状态。Composer 只允许 running 或 waiting_permission 排队，而 waiting_input 会被锁定（`sessionComposerState.ts:37-41,58-63`）。

最小修复是保留 waiting_permission。若必须统一为 waiting_input，则 event patch 需携带 wait kind/pending permission 标志，notifier、Goal bridge、Composer lock/queue 全部按该标志判断，并增加投影后 SSE 的集成测试。
