# AgentSession 终态收敛后的 handoff 与 timeout 原子性

本次重构将 AgentSession 的历史 `blocked`/`paused` 统一收敛为 `completed`，同时让 Run/Step 保留详细终态，并删除 Session pause 控制面。复审确认上一轮的 `waiting_permission` 跨层投影问题以及 legacy migration/pause API 问题已经关闭；按产品要求，Synax 的公开失败、取消和中断投影为 `completed` 不构成问题。Forced handoff 与 permission timeout 的成功路径均已补齐，但两个路径的持久化边界仍允许半结算。

Watch for: **[confirmed, High]** forced Goal continuation 先启动 Run、后消费队列项，消费失败会让同一输入继续留在队列并可能重放；**[confirmed, High]** permission timeout 先永久解决 permission、后在另一事务结算 lineage，后半失败会留下无法再次处理的 waiting execution。

**Verdict**: NEEDS_CHANGES

## High-level view

`round_yielded` 上的 forced item 现在会替换系统 continuation，普通队列 dispatcher 不会同时启动第二个 Run；但 Run admission/launch 与 queue removal 分属两个提交点，故障时无法保证输入只转移一次。

权限超时的成功路径会把 Step 置为 blocked、Tool 置为 denied、Run 置为 blocked，并把 Session 收敛为 completed。Permission resolution 和 `permission_resolved` 事件却发生在 lineage 事务之前，任一后续写入失败都会形成不可重试的半结算。

## Forced Goal continuation 的 queue-to-Run 转移仍非原子

**[confirmed, High]** `submitGoalContinuation` 先调用 `this.submit(...)`（`api/services/agent-runtime/run-coordinator.ts:173`）；`submit` 会持久化 accepted Run，并在返回前通过 `launch` 注册 owner。随后才调用 `inputQueueService.take(...)` 和 `clearForceInject(...)`（`run-coordinator.ts:175-176`）。如果 take 在 Run 已启动后失败，外层 finally 只记录 handoff 错误，新 Run 仍继续执行，而 forced item 与 marker 留在队列；下一次 handoff 会再次选择同一 item，Work 若已结束也可能由普通队列把它作为独立 turn 重放。

如果 `submit` 在启动前失败，item 会保留，但 `dispatchQueuedInput` 拒绝最新 Run 为 `round_yielded` 或 Work 仍 active 的状态（`run-coordinator.ts:86-88`）。调用栈退出后没有 owner 或自动重试触发器，输入不会丢失，却会停在队列中。现有 rollback 测试只覆盖普通 dispatcher 内的 admission + take 事务（`api/services/agent-runtime/__tests__/run-coordinator.test.ts:100-112`），没有覆盖 `submitGoalContinuation` 的 take/launch 失败。

最小修复是把 forced item 到 accepted queued Run 的转移做成单个 SQLite 事务：按稳定 request ID 执行 `acceptRuntimeRun`、`take` 和清除 marker，提交后只 launch 返回的同一个 Run。Launch 失败时保留可由 coordinator 重启的 queued Run，而不是同时保留原 queue item；增加 take 与 launch 失败注入测试，断言输入最终只执行一次。

## Permission timeout 在 permission 与 execution lineage 之间可能断裂

**[confirmed, High]** sweeper 在事务外先调用 `permissionPolicy.reply`（`api/services/agent-runtime/permission-timeout-sweeper.ts:47-53`），再 append `permission_resolved` 事件（`permission-timeout-sweeper.ts:54-65`），直到 `runtimeTransaction`（`permission-timeout-sweeper.ts:68`）才更新 Step、Tool、Run 和 Session。若事件写入或事务内任一 lookup/update 抛错，permission 已带 `resolved_at` 和 reject 结果，不再满足 sweeper 的 `resolved_at IS NULL` 查询；lineage 仍可保持 waiting_permission，后续 sweep 不会重试，用户也无法再次回复。若事件已成功、lineage 后失败，消费者还会收到一个未完成 execution settlement 的 resolution 信号。

当前测试把 transaction mock 成直接调用函数，只断言各 update 被调用（`api/services/agent-runtime/__tests__/permission-timeout-sweeper.test.ts:60-64,103-126`），无法发现前半已提交、后半回滚。最小修复是把 `permissionPolicy.reply` 与 Step/Tool/Run/Session 更新放进同一个 `runtimeTransaction`，只在提交成功后发布事件；用真实 SQLite fixture 注入 lineage 更新失败，断言 permission 一并回滚且下一次 sweep 仍能处理。
