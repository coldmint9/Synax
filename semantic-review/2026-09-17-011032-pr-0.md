# AgentSession 终态收敛与 handoff 原子化最终复核

本次最终复核只覆盖 forced Goal handoff、permission timeout lineage 结算，以及 AgentSession `blocked`/`paused` 收敛三个产品约束，并排除 permission-tier 与 Work runtime 的无关改动。Forced queue item 到 accepted Run 的数据库转移已经原子化，permission timeout 也已把 permission 与 Run/Step/Tool/Session 更新放入同一事务，旧 Session 状态和 pause 控制面则完成迁移。剩余问题位于数据库 commit 之后、内存 owner 建立之前：同步 launch 失败会留下当前进程无法重新启动的 queued Run。

Watch for: **[confirmed, High]** forced handoff 在 commit 后同步 launch 失败时会被搁置到下次进程重启；同 request ID 重试命中 reused 后不会再次 launch。

**Verdict**: NEEDS_CHANGES

## High-level view

Forced handoff 现在以稳定的 `goal-force-input:<itemId>` request ID，在一个外层 SQLite 事务中完成 Run admission、指定 queue item 删除和 force marker 清理，事务返回后才建立 owner。**[confirmed, High]** 这个边界消除了上一轮的双份所有权重放路径，但 reused Run 被无条件视为无需启动，使 commit 后 launch 失败无法在当前进程内恢复。

Permission timeout 路径在同一个 `runtimeTransaction` 中解决 permission，并同步终结 Step、Tool call、Run 与 Session；`permission_resolved` 事件只在事务成功返回后发布。Run/Step 仍可保留 `blocked`，Session 则落为 `completed`，`waiting_permission` 与 `waiting_input` 没有被互相投影。

AgentSession schema 和前端公开类型均已删除 `blocked`/`paused`。迁移 0032、store 读写边界、SQL 列表投影和前端 patch 都将历史值归一为 `completed`；agent-runtime protocol、route、runtime client 和 session runtime 的 pause 操作已删除，旧 route 返回 404。

## Forced Goal handoff 的 committed Run 缺少进程内重启路径

**[confirmed, High]** `submitGoalContinuation` 的 forced 分支已将 `acceptRun`、`inputQueueService.take` 和 `clearForceInject` 包在同一个外层事务中，并在该事务返回后调用 `launchAccepted`（`api/services/agent-runtime/run-coordinator.ts:195-209`）。嵌套的 admission 和 queue service 事务由 savepoint 承接，因此 take/marker 清理失败会回滚 accepted Run，不再留下 Run 与 queue item 两份可执行副本。

`launchAccepted` 对 `accepted.reused` 直接返回（`run-coordinator.ts:65-76`），而第一次调用在事务 commit 后进入 `launch` 时，先读取并更新 Run execution lease，之后才把 owner 放进 `owners`（`run-coordinator.ts:134-144`）。如果该读取或更新同步抛错，forced item 与 marker 已提交删除，Run 保持 queued，owner 尚未建立；finally 只记录 “goal handoff could not be continued”。后续以同一稳定 request ID 重试会得到 `reused: true` 并再次跳过 launch，普通 queue dispatcher 也无法取得已经删除的 item。

启动恢复会识别 queued Run，将原始 input 保留在 Run metadata 并支持显式 continuation（`api/services/agent-runtime/runtime-recovery.ts:18-60,65-71`），所以进程崩溃后不会静默重放或抹掉 payload。缺口是进程没有崩溃、仅 launch 同步失败的情况：该输入会一直搁置到人工重启。应让 `launchAccepted` 在 reused Run 仍为 queued 且当前无 owner 时幂等启动，或在 launch 失败时立即走同等的 queued-run recovery；增加 execution-lease 写入失败后同 request ID 重试的测试，断言只启动一次。
