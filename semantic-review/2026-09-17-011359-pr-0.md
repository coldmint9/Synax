# queued accepted Run 的同 request ID 启动恢复

本轮只复核上一轮唯一 finding：forced Goal handoff 在数据库提交后、owner 建立前发生同步启动失败时，能否在当前进程恢复。`launchAccepted` 现在会在 reused Run 当前无 owner且仍为 `queued` 时重新启动；forced queue item 的删除与 Run admission 仍保持在同一事务中。active owner 和非 `queued` Run 都不会进入第二次启动，未发现直接相关的新回归。结论：**PASS**。

## High-level view

Forced handoff 仍使用稳定的 `goal-force-input:<itemId>` request ID，原子提交 accepted Run、queue item 删除和 force marker 清理，再在事务外建立 owner。同步 launch 失败留下的 `queued` Run 可由相同 request ID 重试补建 owner；现有 owner 与 persisted Run 状态共同阻止重复启动。

## Commit 后同步启动失败的进程内恢复

`submitGoalContinuation` 的 forced 分支在同一 SQLite 事务内完成 `acceptRun`、指定 item 的 `take` 和 force marker 清理，事务成功返回后才调用 `launchAccepted`。上一轮关注的失败窗口仍只存在于 commit 后到 `owners.set` 之前。

该窗口中的同步异常会留下已持久化、状态仍为 `queued` 且没有 owner 的 Run。相同 input 和 request ID 再次进入 admission 时会通过 input hash 校验并返回同一 Run、`reused: true`；`launchAccepted` 随后读取最新状态并重新调用 `launch`，关闭了只能等待进程重启的搁置路径。

`launch` 在返回前同步注册 owner，因此成功建立 owner 后的同 request ID 重试会命中 `accepted.reused && isActive(sessionId)`；owner 已释放时，已经启动或结束的 Run 不再是 `queued`。两道门槛没有留下同一 accepted Run 建立两个 owner 的同步间隙。

定向运行 `api/services/agent-runtime/__tests__/run-coordinator.test.ts`，18 个测试全部通过，包括 active owner 下同 request ID 去重。
