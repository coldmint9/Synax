# 智能合并决策流程

合并工作区、Git 索引、候选提交和检查结果由程序管理。模型只处理程序返回的冲突决策或失败诊断。

## Worker 工具

| 工具 | 行为 |
| --- | --- |
| `git.merge.worker.next` | 从持久状态自动准备/恢复，遇到未决冲突返回摘要；冲突已暂存则继续合并、执行检查，通过后应用候选。 |
| `git.merge.worker.packet` | 按文件或冲突块分页读取摘要，包含三方冲突片段、邻近上下文和文件版本。 |
| `git.merge.worker.resolveBatch` | 一次提交最多 20 个文件的局部决定；只替换选定冲突块，保留 Git 自动合并内容，然后自动推进。 |
| `git.merge.worker.repairRead` | 读取当前候选失败诊断明确引用的已跟踪 UTF-8 文件，支持合并差异以外的文件。 |
| `git.merge.worker.repair` | 对诊断文件做唯一匹配的文本替换，创建修复提交、清除旧验证结果，然后重新检查并推进；每个合并最多三轮。 |

工具返回的 `decision` 为 `conflicts`、`repair`、`waiting` 或 `done`。后两种状态要求结束当前 worker 回合。既有 inspect/read/resolve 等工具保留为特殊冲突与旧会话的兼容通道。

## 冲突与上下文

文本冲突使用 diff3/zdiff3/普通 merge 标记解析。块 ID 绑定实际内容和位置，文件 revision 绑定当前草稿。批量处理先校验全部文件版本和块 ID，再在仓库锁内串行写入。存在未处理块时只保存草稿，全部解决后才暂存该文件。

冲突包默认最多 10 个文件，响应预算 64 KiB；每个文件最多返回 8 个块。`nextOffset` 继续读取文件，`fileId` 配合 `nextHunkOffset` 继续读取块。长块明确标记为截断预览，模型需要通过 read 补读上下文，不能把预览作为完整文件覆盖。二进制和结构冲突可选择整文件，普通文本必须按块决定；无法安全解析的文件转人工/兼容流程。

## 验证和恢复

所有检查结果绑定候选树。修复只发生在隔离工作区，不能直接修改目标分支、跳过检查或访问仓库外路径。诊断路径必须来自当前失败检查，并且是已跟踪的常规文本文件；符号链接、二进制、超过 2 MiB 的文件不进入自动修复。

候选修复先保存父提交、文件清单和提交说明。写入期间停止会尝试恢复仅由本次操作修改且未被外部再次修改的内容。进程中断后保留真实状态；完整的修复提交可按日志核对恢复，未完成或陌生修改需要检查，不能擅自重置。

自动流程通过 Git 状态、来源步骤、候选提交和检查结果判断进展，版本计数自增不算进展。失败检查不会在代码未修改时自动重跑。合并只读工具可有界并发，批量解决、修复、推进等写操作保持互斥。

规则驱动的品牌/版本迁移、锁文件再生成和 rerere 复用不属于这次首版范围。

## 启动栅栏与卡片恢复

合并执行器归属于发起它的会话。父会话是否停止只有一个判定来源：`parent-fence.ts` 的 `parentStopReason`（`runtimeControl` 存在，或状态为 `paused`/`stopping`/`cancelled`/`interrupted`/`failed`）。`manualStop` 是证据不是栅栏：每个停止入口都会同时写入停止状态，而用户在新回合继续对话时该标记会被清除，因此残留标记不会挡住本回合允许进行的合并。

被栅栏拒绝且尚未启动的任务会写入 `status=failed` 的执行记录并带真实原因，卡片因此可显示原因并继续推进；已有执行记录的任务不覆盖其停止意图。无执行记录的草稿卡执行「继续/开始合并」时进入 worker 并由其 `prepare` 步骤开始合并，不会走 MR 级恢复；MR 级 `resume` 对草稿只做一次核对，不再抛出或以「does not need recovery」污染卡片。

## 跑通前置条件

- 必须配置至少一个验证命令；worker 从不跳过验证，缺省会停在配置阶段等待 `git.merge.configure`。
- 目标分支若已在其他工作区检出，需要显式允许，否则按 `TARGET_BUSY` 停止。
- 目标或来源分支在创建后移动会得到 `STALE_PLAN`；旧方案保留，需要重新规划而不是恢复。
